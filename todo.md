- [ ] Decide whether the Stop-hook rewriter should carry two contracts instead of one, and only then whether it can pick between them reliably enough to be worth it.

  The second contract would be a deliberation shape for brainstorming and design turns, alongside the existing status/digest shape for turns reporting work. Roughly: the question being decided → the options with their costs → the recommendation and why → what is still open → `Watch out`. This is not invented; it is `AGENTS.md` §9's own escalation form in FirstMate ("Lead directly with concrete evidence, then the consequence, options when applicable, and a recommendation"), which sits beside the four-section `/bearings` status contract rather than replacing it. FirstMate's whole pattern is a small set of named contracts with one selected per situation, so a second contract is the natural next step — see [`docs/firstmate-reporting-architecture.md`](docs/firstmate-reporting-architecture.md) for that architecture, what was taken from it, and the measurements behind the current single-contract prompt.

  Selection is the crux, not the second shape. A design discussion rendered as a status report is worse than no rewrite at all: it fabricates a settledness the turn did not have, and the reader loses the actual reasoning. The current prompt therefore deliberately offers the model **no** format branch — that judgement was what the previous model tier handled worst. Sonnet 5 is stronger, but that must be measured, not assumed.

  Classification accuracy is the top-line metric, above retention. Hand-label the corpus as status / discussion / mixed, run the prompt, and report the confusion matrix. Mixed messages will be common and need an explicit tie-breaker written into the prompt, not left to the model. If selection proves unreliable, fall back to a single contract and close this out — a reliable one-shape rewrite beats an unreliable two-shape one.
- [ ] Port `screen-verify`'s staging code to Hyprland's Lua IPC. The `.conf` -> Lua migration landed and took the rest of the repo with it, but `pkgs/screen-verify/screen_verify_lib/stage.py` and `watch.py` were deliberately left behind; `preview.py` is already done.

  Under the Lua config manager `hyprctl dispatch` no longer takes a legacy dispatcher name -- its argument is evaluated as Lua, so `hyprctl dispatch focuswindow address:0x…` is a *syntax error*, not an action. `hyprctl keyword` is refused outright ("keyword can't work with non-legacy parsers. Use eval."). Nine call sites are affected: `focusmonitor`, `focuswindow`, `movetoworkspacesilent` (three of them), `moveworkspacetomonitor`, `keyword workspace`, and `dispatch exec` with a `[workspace …; noinitialfocus]` rule prefix. `hyprctl output remove`, `monitors`, `clients`, `activewindow` and `getoption` are unaffected.

  Most translations are already verified live on `linglong`: `hl.dsp.focus({ window = "address:…" })`, `hl.dsp.focus({ monitor = … })`, `hl.dsp.window.move({ workspace = N, follow = false, window = … })` (the "silent" variant). Two are not, and are the reason this was deferred rather than improvised: `keyword workspace name:X,monitor:Y,default:true` becomes `hl.workspace_rule({ workspace = "name:X", monitor = "Y", default = true })`, and the rule-prefixed exec becomes `hl.dsp.exec_cmd(cmd, { workspace = "name:X silent", no_initial_focus = true })` -- `hl.dsp.exec_cmd` takes a second table of window-rule effects. Verify both against a live Lua compositor before trusting them: unknown *fields* in a dispatcher table are silently ignored (unknown *values* are rejected), so a wrong key name is a silent no-op, which is exactly how `cycle_next({ prev = … })` nearly shipped.

  The failure is not silent at the top level, which is why deferring was affordable: `hyprctl_quiet` swallows errors by design and degrades staging, and `stage_spawn` raises "The staging launch could not be dispatched; retry with --no-stage". Until this is done, `screen-verify` capture works only with `--no-stage`. The test suite fakes `hyprctl` and asserts on argv (`pkgs/screen-verify/tests/test_cli.py`), so each ported call site needs its expectation updated alongside.

  Reference material, better than the wiki: `share/hypr/stubs/hl.meta.lua` in the `hyprland` package (typed API stub; note dispatcher args are typed only as `fun(...)`, so the wiki's Dispatchers page is the argument-name authority) and `share/hypr/hyprland.lua` (upstream example config). Parse-check with `Hyprland --verify-config --config <file>`; note it validates key strings and config keys but cannot catch a wrong dispatcher *field*.
