- [ ] Add `screen-verify type` and `screen-verify click`, gated on session ownership in code rather than prose. Both must refuse to inject into any window whose address is not session-owned and on the stage; driving an unowned window should require an explicit flag, matching how `--no-stage` already works for capture. The enforcement hook exists today: `screen_verify.py` tracks `pid` and `window.address` per owned process and has `owned_stage_addresses()`. Bare `ydotool` has no concept of a target window and types wherever focus happens to be, which is exactly why this belongs behind `screen-verify` instead of a loose instruction to call `ydotool`.

  Motivation is interaction *in service of* verification, not general computer use: states reachable only after input — a query typed into `rofi`, hover and focus rings, an open dropdown, a dialog's error state — are pixel-verifiable only and currently unreachable, since `screen-verify` can launch and photograph a test surface but cannot drive it. Keep this inside `visual-verification`'s existing restrictive gate; do not generalize that skill into a computer-use skill, whose enabling framing would erode the gate that stops screenshot-spam. Note that input is not reversible the way `preview` snapshot/restore and `end` cleanup are, so ownership confinement is the substitute for restorability. Build it when a real task stalls on it, not speculatively.

  Selection is the crux, not the second shape. The current prompt therefore deliberately offers the model **no** format branch — that judgement was what the previous model tier handled worst. Sonnet 5 is stronger, but that must be measured, not assumed.

  Classification accuracy is the top-line metric, above retention. Hand-label the corpus as status / discussion / mixed, run the prompt, and report the confusion matrix. Mixed messages will be common and need an explicit tie-breaker written into the prompt, not left to the model. If selection proves unreliable, fall back to a single contract and close this out — a reliable one-shape rewrite beats an unreliable two-shape one.

- [ ] Migrate the Hyprland config from `.conf` to Lua. Investigated and deliberately deferred; this entry exists so the research is not re-derived.

  The trigger is a nag on every boot: `You are using the .conf config format, support for which will be removed in Hyprland 0.57.` The string lives in the binary and is delivered through the startup nag path, not the log — which is why `hyprctl configerrors` is empty and it appears in no journal — and it is rate-limited via `~/.local/share/hyprland/lastNag`. A corroborating log line reads `[cfg] Lua config not found, using legacy config at ~/.config/hypr/hyprland.conf`. Currently on Hyprland 0.56.1 (built 2026-07-27, commit `5c9377c15f85c50648f35ca5a213754f95b93ca0`), so the deadline is 0.57 and there is time; do not rush it into a partial state. Note in passing that `windowrulev2` is the only other deprecation string in the binary and it appears here only on commented-out lines (453, 457) of `hyprland.conf` — not implicated, do not chase it.

  The replacement is `~/.config/hypr/hyprland.lua` using the `hl.*` API (`hl.config{...}`, `hl.bind(...)`, `hl.monitor{...}`, `hl.dsp.*` dispatchers). Read the local references rather than upstream docs: the Hyprland store path ships `share/hypr/hyprland.lua`, a 356-line reference config, and `share/hypr/stubs/hl.meta.lua`, a 1771-line typed API stub. That path is version-pinned and moves on a nixpkgs bump, so locate it from the current `hyprland` package instead of hardcoding the hash.

  Three reasons it was deferred, and why it is all-or-nothing. First, there is no incremental path: no `source`/`keyword`/legacy-include helper exists anywhere in the API stub, so once `hyprland.lua` exists it replaces `hyprland.conf` wholesale and no partial slice silences the nag. Second, the failure mode lands on the user — the binary contains `Emergency mode tripped: A lua config error resulted in no binds being registered. Emergency binds active: SUPER + Q`, and because `~/.config/hypr` is an out-of-store symlink a wrong file goes live on merge with no rebuild, so a mistake reaches the compositor immediately and a mistranslated dispatcher drops a bind *silently*. Third, the scope reaches into Nix, not just dotfiles: ~400 effective lines across `dotfiles/hypr/hyprland.conf` (238 non-comment lines), `themes/dark.conf` (64), `themes/light.conf` (43), `themes/current.conf` (64), plus generated `role.conf` and `wallpaper.conf`, with include order in `hyprland.conf` at line 17 `current-theme.conf`, line 19 `wallpaper.conf`, line 277 `role.conf`. On the Nix side `home/programs/dotfiles.nix:111` generates `hypr/role.conf` as `.conf` text, `home/desktop/theming.nix` drives ~20 `hyprctl keyword` calls (`general:col.active_border`, `decoration:screen_shader`, `env XCURSOR_THEME,…`) plus a systemd-tmpfiles symlink at line 328, and `home/desktop/phosphor-switch.nix` is implicated too.

  Two questions must be answered before starting, because either may change the whole design: whether `hyprctl keyword` still works under the Lua manager, and whether the theme-switch mechanism — symlink one of two `.conf` files and reload — has any Lua analogue. Neither was confirmed. The most useful practical find is a safe validator: `Hyprland --verify-config --config /path/to/hyprland.lua` is verified working and Lua-aware (`[cfg] Config is lua, loading lua mgr` … `config ok`) and is non-destructive, so a migration can be parse-checked before going near a live compositor. When picked up, do it in one pass with a full budget window: `--verify-config` first, then a live `hyprctl reload` test on the home desktop (`linglong`) rather than the laptop — push the branch via the peer remote, use a scratch worktree, temporarily repoint `~/.config/hypr` at it, verify, then restore the symlink and confirm the restore took.
