## 2. 架构：色板阶梯

`home/palettes.nix` 是唯一色彩来源。一个 profile 是**十级递增亮度的阶梯**，每个终端槽位按**级名**而不是按十六进制赋值：

```
background < deepSurface < raisedBlack < subtleBorder < mutedText
          < secondaryText < accent < foreground < bright < hot
```

这样换磷光只需提供十个颜色，就能继承此前针对琥珀调好的全部强调层级，包括几个刻意的「不规则」安排：

- `raisedBlack` —— ANSI 黑，抬离背景，好让用 ANSI 黑绘制的选中行仍然可见
- `secondaryText` —— ANSI 白，**压到**前景之下，让 SGR-37 的次要文本读起来确实是次要的
- `hot` —— ANSI 亮绿，**抬到**前景之上，让高亮选中项能区分出来
- `bright` —— ANSI 亮蓝，位于前景与 hot 之间，让模糊匹配片段读作强调而非刺眼

因为这些选择是**位置性**的，换 profile 会自动带过去，不需要重新调教依赖它们的程序。

## 3. 夜间模式：把绿色变换成琥珀

### 3.1 原理与根本限制

hyprsunset 的 CTM 是**严格对角**的：

```
k_r = gamma × blackbody_r(T)/255
k_g = gamma × blackbody_g(T)/255
k_b = gamma × blackbody_b(T)/255
```

屏幕上每一个颜色都乘同样的三个增益。**绿色无法被精确旋转成琥珀**，因为两条阶梯的内部色相走向不同：绿色需要乘的 red:green 比值，在阶梯上从暗端的 1.80 变化到中间调的 3.66，而一个 CTM 只能给出一个值。

这就是无法完美匹配的根本原因，不是调参没调好。

### 3.2 三个不可回避的约束

1. **1900 K 以下蓝色被强制归零。** 任何暖到能让红色压过绿色的色温，都已经把蓝色截断了。所以变换后的琥珀比原始琥珀更纯（少了琥珀本身那一点蓝色分量）。
2. **gamma 必须 > 1。** CTM 在 gamma ≤ 100% 时只能衰减，红色永远压不过绿色，出来的是**橄榄色**不是琥珀（前景会落在 `#585700`，R=88 G=87）。
3. **gamma > 1 会削顶。** 阶梯最亮的两级红色通道饱和，亮端被压缩；同时红色被放大到屏幕上所有内容，照片和视频在夜间模式下会过曝。

### 3.3 拟合结果（1100 K / 280%，鲜亮绿）

| 级 | 绿色 | 夜间模式后 | 琥珀目标 |
| --- | --- | --- | --- |
| background | `050806` | `0E0700` | `080705` |
| mutedText | `193F20` | `463600` | `6E501D` |
| accent | `3D8E48` | `AB7900` | `BE842A` |
| foreground | `4BAE55` | `D69300` | `D99B32` |
| hot | `86E68C` | `FFC300` | `FFD064` |

对照原始琥珀（含蓝色分量）平均色差 13.9；对照**去蓝琥珀**（任何无蓝变换的理论上限）屏幕上实际色差 **10.0**，其中前景那一级只有 3.4，基本到了察觉阈值附近。

> 注：色差对照两种目标会给出方向相反的结论。灰化版对「含蓝琥珀」更好（13.2 vs 13.9），但对「屏幕上实际看到的去蓝琥珀」反而更差（11.7 vs 10.0），因为 gamma 从 280% 降到 200% 后整体偏暗。引用数字时要说明用的是哪个目标。

## 4. 关键技术发现

这四条都是踩过坑之后确认的，值得记住。

### 4.1 CTM 不出现在截图里

hyprsunset 的 CTM 在**扫描输出（scanout）**阶段应用，不在合成缓冲区里。实测：2000 K 开启前后两张截图**逐像素完全相同**（0 个像素不同）。

**后果**：夜间模式无法用截图验证。替代验证路径是读服务自己打印的那行日志：

```
┣ Calculated the CTM to be [mat3x3: 2.8, 0, 0, 0, 0.84989333, 0, 0, 0, 0]
```

模型推算值与实测日志逐位吻合。这条路径在本 session 里用过三次（1100 K/280%、1400 K/200%、再回到 1100 K/280%），每次都对上了。

### 4.2 色温被整数量化到百位

`matrixForKelvin` 里是 `temp /= 100`，**整数除法**。所以 1100 K 和 1199 K 产生完全相同的矩阵，而 1080 K 会**静默地**当成 1000 K 处理。

这个坑是靠「模型预测的 CTM 与日志不符」发现的——第一版发的是 1080 K，日志里的 k_g 对不上，回头才查出量化。把量化加进模型重新扫描后，最优点落在 1100 K。

**规则：色温永远写 100 的整数倍。**

### 4.3 `--gamma_max` 的「200% 上限」只是文档

`main.cpp` 里 `maxGamma` 解析后直接赋值，**没有任何 clamp**。当前配置正是靠这一点把 `max-gamma` 设到 300，好让夜间 gamma 用 280%。

### 4.4 `max-gamma` 的默认值是 100，不是 200

`ConfigManager.cpp`：`addConfigValue("max-gamma", Hyprlang::INT{100})`。

所以**只要 gamma 超过 1.0，就必须显式写 `max-gamma`**，否则 hyprsunset 直接拒绝整个 profile。这一行删不掉——过程中一度说「灰化后可以去掉这个覆盖」，那是错的：改成 200 也仍然需要这一行，区别只在于 200 落在文档声明范围内、300 则超出。

## 5. 并排对比：为什么需要预补偿

CTM 是**按输出（per-output）**设置的（`sendSetCtmForOutput`），没有 per-window 或 per-workspace 作用域。单显示器下，屏幕上所有内容必然共享同一个矩阵——**夜间模式无法只作用于一个工作区**。

绕过办法是**反向预失真**：`previewProfiles.amberViaNight` 是琥珀**除以**夜间增益。夜间模式开启时，用这个色板的终端会渲染成真实琥珀，而旁边普通绿色终端渲染成变换后的样子。两个窗口处在同一个 CTM 下，对比是真实的而非模拟的。

**诚实的局限**：蓝色增益为 0，无法做除法，所以参考窗口也没有蓝色。这不是偷懒——夜间模式会湮灭屏幕上所有内容的蓝色，任何在它之下显示的参考都不可能带蓝色。所以这个对比在色相和明度上是诚实的，对琥珀那一点蓝色分量则保持沉默。

`home/palettes.nix` 里用 Nix 手写了十六进制运算来推导这些色板，所以它们不会和增益脱节。但那三个增益值本身是从日志**抄写**的——Nix 没有对数内置函数，算不出黑体曲线。**改 `nightTemperature` 或 `nightGamma` 后必须重新抄一次。**

## 6. 昼夜节律分析

黑视素（melanopsin）主要响应蓝光、部分响应绿光、几乎不响应红光。按 sRGB 三原色峰值波长的黑视素敏感度加权（R≈0.01, G≈0.50, B≈0.89，作用于线性光），估算一个典型终端画面：

| 设定 | 相对白天的黑视素暴露 |
| --- | --- |
| 常规 2700 K 夜灯 | 0.32× |
| 常规 1900 K / gamma 100% | 0.17× |
| **当前：鲜亮绿 1100 K / 280%** | **0.50×** |
| （曾试过）灰绿 1400 K / 200% | 0.40× |

**结论**：没有抵消护眼作用，但只拿到常规夜间滤镜大约一半的收益。原因是一场拉锯——1900 K 以下蓝色被打到**精确的零**，这比任何常规夜间模式的蓝光削减都彻底；然后 gamma 放大又通过绿色通道还回去一部分，而绿色磷光的能量恰恰主要在绿色通道。

> 注意：这些数字是三原色峰值近似，不是分光光度计读数。**选项之间的比值**可信，绝对值不可信。

## 7. 饱和度权衡（已决：留在鲜亮版）

**最终决定**：回到鲜亮版（前景 `#4BAE55`，饱和度 0.57），夜间配 1100 K / 280%。灰化虽然能让琥珀更准、也能压低 gamma 需求，但代价是蓝光变多、白天节律负担上升，而且观感上更像「褪色的旧显示器」而不是真正的窄带磷光。下面这一节保留完整的量化过程，供以后重新权衡时参考。



灰化是降低 gamma 需求的关键杠杆。所需 gamma ≈ `琥珀的红 / 绿色的红` = 217 / green_R：

- 饱和绿 R=75 → 需要 gamma 2.89
- 灰绿 R=88 → 需要 gamma 2.47

同样卡在 200% 上限时：

| 绿色 | 最优设定 | 色差 | 夜间黑视素 |
| --- | --- | --- | --- |
| 鲜亮绿（最终采用） | 1400 K / 200% | 18.6 | 0.42× |
| 灰绿 | 1500 K / 200% | 11.0 | 0.46× |

灰度扫描（色差为 200% 上限内可达的最优）：

| 相对现在 | 前景 | 饱和度 | 色差 | 夜黑视素 | 昼黑视素 |
| --- | --- | --- | --- | --- | --- |
| −0.30（≈鲜亮版，最终采用） | `47AF51` | 0.59 | 18.9 | 0.43× | 0.96× |
| −0.15 | `4FAB59` | 0.54 | 14.8 | 0.41× | 0.98× |
| 0（灰化版） | `58A860` | 0.48 | 11.0 | 0.46× | 1.00× |
| +0.15 | `61A567` | 0.41 | 7.8 | 0.50× | 1.03× |
| +0.30 | `69A16F` | 0.35 | **5.3** | 0.53× | 1.06× |
| +0.45 | `729E76` | 0.28 | 4.8 | 0.57× | 1.11× |

越灰 = 蓝色分量越多 = 白天和夜里都更伤节律。+0.45 之后不再改善，因为色温已顶到 1900 K 的蓝色截止点。

**候选：再灰一档（d=+0.30）**，可在 gamma 200% 内做到色差 5.3：

```
background     #070907      secondaryText  #436949
deepSurface    #0A0D0B      accent         #56845B
raisedBlack    #0E120F      foreground     #69A16F
subtleBorder   #1A241D      bright         #84BF8A
mutedText      #304735      hot            #A5DCAA
```

搭配夜间 1700 K / 200%。**此项未实施** —— 最终选择了相反的方向（回到鲜亮版）。
