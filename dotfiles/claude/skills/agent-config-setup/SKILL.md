# Agent Configuration

## Claude

The tracked source of truth is `/home/andongni/.nixos-config/dotfiles/claude/`. Home Manager module `home/programs/mutable-configs.nix` wires it into `$CLAUDE_CONFIG_DIR` mostly via `mkOutOfStoreSymlink` — an out-of-store symlink pointing at this repo checkout (`osConfig.portable.configDir`) instead of a store copy. **Edits to symlinked files are live immediately; no rebuild needed.**

- Symlinked (edit under `dotfiles/claude/`, changes are live at once): `CLAUDE.md`, `statusline.sh`, `skills/`, `commands/`, `output-styles/`.
- Materialized, not symlinked: `settings.json`. `dotfiles/claude/settings.json` is the tracked non-secret baseline for the standard and Matt Pocock profiles; `dotfiles/claude-gpt56/settings.json` is the separate GPT-5.6 baseline. `home.activation.claudeSettings` (in `mutable-configs.nix`) jq-injects the current desktop theme (`dark-ansi` / `light-ansi`) into the applicable baseline and installs the result as an ordinary mutable `0600` file at each `$CLAUDE_CONFIG_DIR/settings.json` on every activation; `home/desktop/theming.nix` (`setClaudeTheme`) re-applies just the theme on every dark/light switch. Theme is the only intentional runtime variance — edit the tracked baseline, not the runtime copy, and rebuild to propagate non-theme changes.
- Machine-local mutable state, not sourced from the repo, not configuration to manage here: `.claude.json`, `.credentials.json`, `history.jsonl`, `projects/`, `sessions/`, `plugins/` (`installed_plugins.json`, `known_marketplaces.json` — managed via Claude's `/plugin` command), and caches. There is no `agents/` directory under `$CLAUDE_CONFIG_DIR`.

## Config directories

Claude has no Codex-style named profiles; each `CLAUDE_CONFIG_DIR` acts like a separate profile directory.

- Default: `/home/andongni/.config/claude` (default `CLAUDE_CONFIG_DIR`).
- `claude-mattpocock`: `/home/andongni/.config/claude-mattpocock`, selected by the `claude-matt` shell alias in `home/programs/shell.nix`, which sets `CLAUDE_CONFIG_DIR="$HOME/.config/claude-mattpocock"` before invoking `claude` (it's an alias, not a separate binary). `cly` / `clty` are `claude` / `claude-matt` with `--dangerously-skip-permissions`.
- `mutable-configs.nix` wires the same dotfiles sources into `claude-mattpocock` with `force = true`, but skills are wired per-skill, not as a whole `skills/` directory link: only `agent-config-setup`, `nix-environment-setup`, and `bro` (from `dotfiles/claude/skills/`) plus `visual-verification` (from the repo-root `skills/visual-verification`) are shared. Every other skill under `claude-mattpocock/skills` is independent and mutable, managed outside this repo.
- `claude-gpt56`: `/home/andongni/.config/claude-gpt56`, launched by the dedicated `claude-gpt56` binary (`clg`; `clgy` skips permission checks). Like `claude-mattpocock`, it wires skills per-skill, not as a whole `skills/` directory link: it shares `agent-config-setup`, `nix-environment-setup`, `visual-verification`, and `bro` from the standard profile, plus `commands/`, `output-styles/`, and `statusline.sh`, while its GPT-specific `CLAUDE.md`, materialized settings, credentials, history, sessions, plugins, and caches remain separate. It deliberately has no managed `agents/` directory: Claude Code's built-in agents remain available without custom role presets. Do not copy `.claude.json`, `.credentials.json`, histories, sessions, or plugin/cache directories into it.
- **Adding a skill to every Claude profile takes three wirings, not one.** The default `claude` profile links the whole `skills/` directory, so a new skill placed at `dotfiles/claude/skills/<name>/` appears there automatically (live immediately, no rebuild). But `claude-mattpocock` and `claude-gpt56` link skills per-skill, so each also needs its own `mutable-configs.nix` entry — `claude-mattpocock/skills/<name>` and `claude-gpt56/skills/<name>`. Those are Nix wiring changes, so they require a rebuild to take effect. Forgetting either per-skill profile silently leaves the skill absent there while it works in the default profile.

## Launcher and package

- Launchers: `home/programs/claude.nix` (`writeShellApplication`) — both `claude` and `claude-gpt56` use the Nix-managed Claude Code package and share the same proxy, locale, and `CLAUDE_CODE_*` host environment. The GPT launcher additionally selects its isolated config dir, reads the local client key, starts the local gateway, supplies friendly semantic-slot metadata, and advertises `effort`, `xhigh_effort`, and `max_effort` support through Claude Code's exact `ANTHROPIC_DEFAULT_*_MODEL_SUPPORTED_CAPABILITIES` interface. Gateway model discovery is unset, and `CLAUDE_CODE_SUBAGENT_MODEL` remains unset so built-in Agent calls can select a semantic slot instead of inheriting one global pin. Built-in subagents inherit the session effort because the Agent tool has no per-call effort argument.
- Package derivation: `pkgs/claude-code.nix`.
- GPT gateway: `pkgs/cli-proxy-api.nix` packages the pinned no-plugin CLIProxyAPI binary. `home/programs/cli-proxy-api.nix` runs it as a loopback-only user service, renders its secret-bearing config only under `$XDG_RUNTIME_DIR`, stores the local client key under `$XDG_STATE_HOME`, and stores Codex OAuth data under `$XDG_DATA_HOME`. Run `cli-proxy-api-codex-login` once to authorize Codex. The gateway retains exactly three base aliases: `claude-gpt-5-6-sol`, `claude-gpt-5-6-terra`, and `claude-gpt-5-6-luna`. `dotfiles/claude-gpt56/settings.json` restricts `availableModels` to `opus`, `sonnet`, and `haiku`, defaults to `opus` with high effort, and uses `modelOverrides` to map Claude Code 2.1.217's canonical IDs (`claude-opus-4-8`, `claude-sonnet-5`, and `claude-haiku-4-5-20251001`) to those gateway aliases. The canonical IDs are version-specific: after a Claude Code upgrade, verify all three direct semantic routes and built-in Agent model overrides against live `modelUsage`, then update the keys if necessary. Model and effort are independent; Claude Code's native session effort is translated upstream without alias-specific `reasoning.effort` overrides.

## Codex

Tracked source of truth: `/home/andongni/.nixos-config/dotfiles/codex/` (plus `dotfiles/agents/skills` for the shared skill pool). `mutable-configs.nix` wires it into `~/.codex` the same way: symlinked content is live immediately, no rebuild needed.

- Symlinked: `AGENTS.md`, `rules/`, `skills/` — 14 tracked Codex-specific skills (includes this skill, `bro`, and `sync-mattpocock-skills`).
- Profiles are symlinked too (since 2026-07): `~/.codex/<name>.config.toml` is an out-of-store symlink to `dotfiles/codex/profiles/<name>.config.toml`, so profile edits are live immediately, no rebuild. The list is still hardcoded (`codexProfileNames` in `mutable-configs.nix` — adding or removing a profile file requires editing it too, then a rebuild for the link itself; Home Manager prunes dropped links automatically). 5 tracked profiles: `last30days`, `lavish-axi`, `mattpocock`, `superpowers`, `understand-anything-codegraph`. Codex canonicalizes skill paths at scan time, so symlinked profiles behave identically to the old materialized copies. Symlinking is also write-safe: every runtime config persistence in v0.144.5 targets the base `~/.codex/config.toml`, never a profile file — `codex mcp add` writes the global file even with `--profile`, `codex features disable` rejects `--profile` outright, and the TUI `/skills` enable/disable popup persists through an app-server config-write RPC that defaults to the base `config.toml` (verified empirically in a scratch `CODEX_HOME` plus binary inspection). So in-session toggles land in the unmanaged machine-local file and the repo stays static. Caveat: because profiles layer over base, a `/skills` toggle written to base can be masked by an explicit profile-level `enabled` stanza for the same skill. Note `flake.nix` sets `home-manager.backupFileExtension = "backup"`, so force-replaced files leave `*.backup` siblings behind (safe to delete).
- `~/.codex/shared-skills` is a separate out-of-store symlink to `dotfiles/agents/skills` — a curated ~36-skill pool, not Codex-specific. Codex cannot load directly from it (`shared-skills/<name>` profile entries are inert; see next bullet). Pool skills reach Codex via **per-profile skill groups**: relative symlinks inside the scanned root, grouped per profile (`dotfiles/codex/skills/mattpocock/<name>` → `../../../agents/skills/<name>`; flat `dotfiles/codex/skills/last30days` likewise). The scan recurses into subdirectories, so grouped skills load like any other — then base `~/.codex/config.toml` disables each by name and the owning profile re-enables it, yielding per-profile activation. Adding a pool skill to a profile = add the symlink + a base disable + a profile enable (skill frontmatter `name:`, which for the current 24 equals the dir name). It's CLI-only: Codex Desktop's `CODEX_HOME` is `~/.codex-desktop`, which never reads `~/.codex`, so Desktop never sees any of this.
- The engine auto-scans two sources regardless of profile: `$HOME/.agents/skills` as a USER-scope source (independent of `CODEX_HOME`) and bundled `.system` skills under `$CODEX_HOME/skills/.system` (verified in v0.144.5 source, `core-skills/src/loader.rs`) — anything placed at `$HOME/.agents/skills` would auto-load into every Codex surface, including Desktop, with no per-skill opt-out, which is why that path must never exist on this machine. The shared pool instead lives at `dotfiles/agents/skills`, reached only via `~/.codex/shared-skills`. `~/.codex/skills` itself is also auto-scanned: every skill there loads by default in every session, no stanza needed. Select a profile with `codex --profile <name>` — the profile file is **layered on top of** the base `~/.codex/config.toml`, which always applies; profile keys override base keys. `[[skills.config]]` semantics, established empirically on v0.144.5 (2026-07, via `codex debug prompt-input` and `--strict-config`): only `name = "<skill>"` selectors work, and only to toggle skills already in the scanned index (`~/.codex/skills` including `.system`, plus installed plugins' skills). `path = ...` selectors are entirely non-functional — they silently no-op even with canonical absolute paths, even for disabling scanned skills. No config key adds scan roots (`skills.extra_roots` etc. are rejected as unknown fields; the only extra-roots mechanism is the app-server RPC `skills/extraRoots/set`, unavailable from config.toml) — hence the shared-skills pool is unreachable from profiles.
- Mutable, not sourced from the repo: `config.toml`, `auth.json`, sqlite state, `history.jsonl`, `sessions/`, caches. The base `config.toml` deliberately carries CLI-wide opt-outs (2026-07): the GUI-only `@openai-bundled` plugins are disabled (`browser` targets the ChatGPT in-app browser that only exists in Desktop; also `computer-use`, `sites`, `visualize`), and `features.remote_plugin = false` kills the `<recommended_plugins>` account-connector suggestions such as Google Drive — those are ChatGPT account-level connectors, not local files, so directory isolation alone cannot hide them. The five `.system` skills stay enabled (engine default). Preserve these stanzas when touching `~/.codex/config.toml`. (The former `openai` opt-in profile was removed 2026-07 — it predated Desktop's isolation into `~/.codex-desktop` and became redundant.)
- `@openai-bundled` plugins ship with the **Desktop app**, not the CLI npm package — the CLI has no `openai-bundled` marketplace of its own. The CLI's `chrome` and `deep-research` plugins are installed from a static local snapshot at `~/.codex/local-marketplaces/openai-bundled` (copied 2026-07 from `~/.codex-desktop/.tmp/bundled-marketplaces/openai-bundled` plus the cached `deep-research` payload, registered via `codex plugin marketplace add`). It does not auto-update; refresh the snapshot manually after Desktop updates if newer plugin versions are wanted.
- `dotfiles/codex/skills/.system/` on disk is engine-owned: the CLI auto-syncs bundled skills there **through the `~/.codex/skills` symlink** and rewrites the tree on version bumps (hash in `.codex-system-skills.marker`). It is gitignored, untracked, and must stay that way — deleting it is harmless (the engine recreates it).
- CLI package derivation: `pkgs/codex.nix`, wired via `home/programs/codex-desktop.nix` (`home.packages`); Codex Desktop (GUI) uses `pkgs/codex-desktop-isolated.nix` through the same module and keeps its state under `~/.codex-desktop`, isolated from the CLI. Shell alias `cdy` runs `codex --yolo` (bypasses approval prompts, unrelated to profile selection).
- Codex Desktop's `~/.codex-desktop/config.toml` is fresh app-owned mutable state, not repo-managed: nothing in this repo writes to it.
- Claude does not consume the pool: it's not shared with Codex's whole-directory `~/.codex/shared-skills` symlink. If a pool skill is ever needed there, share it the way `claude-mattpocock` shares `visual-verification` today — a per-skill relative symlink inside `dotfiles/claude/skills/`, not a directory-wide link.

## Workflow

1. Locate the tracked source under `dotfiles/claude/` (Claude) or `dotfiles/codex/` / `dotfiles/agents/` (Codex) first; edit there, never a runtime copy under `$CLAUDE_CONFIG_DIR` or `~/.codex`.
2. Keep edits scoped to the requested change.
3. Commit the change so the repo's pre-commit hooks are the verification gate (repo policy) — do this even for changes that are already live via symlink.
4. Rebuild with `sudo nixos-rebuild switch --flake .#system --impure` (or the `rebuild` alias, which targets `/etc/nixos#system` and works from any directory) only when the change touches a materialized file (`settings.json`) or Nix wiring itself (`mutable-configs.nix`, `theming.nix`, `claude.nix`, `cli-proxy-api.nix`, `codex-desktop.nix`, or a package derivation). Pure content edits to already-wired symlinked files (`CLAUDE.md`, `skills/`, `commands/`, `output-styles/`, `statusline.sh`, `AGENTS.md`, `rules/`, `dotfiles/agents/skills/`, `dotfiles/codex/profiles/`) are already live — commit only, no rebuild required.
