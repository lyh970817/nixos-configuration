# Work on the Peer Device

This repository serves two machines and this skill runs in either direction. The machine you are on is the **local host**; the machine you reach over SSH is the **peer host**. Nothing below is home-specific: read the roles at runtime instead of assuming which side you started from.

1. Establish both sides before acting. On the local host record the hostname, the Git checkout, and `/etc/nixos/local.nix` (`portable.role`, `portable.peerHost`, `portable.configDir`). Reach the peer as `ssh <portable.peerHost>` over Tailscale SSH — `ssh dynabook-x30wk` from the `home` role, `ssh home` from the `remote` role — and read the same facts there. Confirm the two roles come back as `"home"` and `"remote"` in some order; if both sides report the same role, stop and report that rather than guessing which is which. SSH lands in `$HOME`, not in the checkout, so every peer-side Git or repository command needs an explicit `cd` into that host's `portable.configDir` (currently `~/.nixos-config` on both machines).

   Ad hoc filesystem access to the peer's home directory does not need manual scp/rsync: `modules/system/peer-home-mount.nix` gives each host a reciprocal SSHFS automount at `~/<portable.peerHost>` (lazy — mounts on first access, over Tailscale SSH, no keys required). Prefer reading/copying through that path over hand-rolled transfers when both hosts are already built with it.
2. Inspect Git state on both hosts before changing or transferring anything. Preserve dirty and untracked files, compare HEAD, branch, upstream, and `origin`, and never reset, clean, overwrite, or silently include unrelated work. Both checkouts must retain the canonical origin `git@github.com:lyh970817/nixos-configuration.git`. Each side also carries a Git remote pointing at the other over Tailscale — `laptoppeer` on the home host, `homepeer` on the remote host. Use whichever peer remote exists on the side you fetch or push from, and never repoint `origin` at a peer.
3. Transfer committed history with normal Git when possible, in whichever direction the work flows: fetch from the peer remote, or let the peer fetch from yours. If the fetching side cannot SSH back to the other, create a Git bundle in a source-side path returned by `mktemp`, create a distinct target-side path with `ssh <peer> mktemp`, copy the bundle there, verify it, and fetch or fast-forward without changing `origin`. Validate each generated path before use, install cleanup traps where practical, and remove only those exact paths on both hosts; never use a fixed temporary filename, glob, or broad temporary-directory cleanup.
4. Keep edits role-aware in both directions. Change shared modules only when behavior is genuinely shared; gate home-only packages, services, hardware, desktop behavior, and secrets on `portable.role == "home"`, and gate remote-only behavior on `portable.role != "home"`. Per-machine hardware workarounds belong in `portable.quirks.*` in the untracked `/etc/nixos/local.nix`, not in a role gate. Do not make either role emulate the other merely to simplify a transfer, and do not drop a role gate just because the host you are standing on does not exercise it.
5. Copy secrets only through an explicit allowlist, the same list in either direction: `secrets/coding-cli/`, `secrets/mihomo-cache/`, and `secrets/hyprwhspr-credentials.json`. The allowlist is a ceiling, not a requirement — a host legitimately holds fewer of these than its peer. Keep credential directories mode `0700` and credential files mode `0600`, preserve ownership, compare without printing secret contents, and never stage or commit copied secrets. Never recursively mirror `secrets/`, use a deleting sync, or copy `secrets/mihomo-config.yaml` between hosts.
6. Commit each scoped configuration change before rebuilding so pre-commit hooks provide the verification gate. Preserve unrelated work, synchronize the resulting committed history between both checkouts, then rebuild both machines: rebuild the local host with `rebuild` and rebuild the peer interactively with `ssh -t <portable.peerHost> 'sudo nixos-rebuild switch --flake /etc/nixos#system --impure'`. This synchronization and two-host rebuild are always required before reporting completion, including for role-gated changes that only take effect on one side. If either rebuild fails, make a follow-up fix commit before rebuilding both machines again.
7. Treat any edit to a host's live `secrets/mihomo-config.yaml` as connectivity-critical on that host; both machines run mihomo. Bootstrap a known-good baseline there with `sudo mihomo-guard keep`. Apply an edit only with `sudo mihomo-guard try` (or `sudo mihomo-guard try 120` for an explicit timeout), which briefly restarts all TUN traffic and arms the default 90-second auto-revert. If connectivity remains good, immediately run `sudo mihomo-guard keep`; if the edit is bad but the session survives, run `sudo mihomo-guard revert`; if connectivity is lost, do nothing and let the timer restore the last-good file and restart mihomo. Run the guard commands on the host that owns the file, through `ssh -t` when that host is the peer, and expect a peer-side `try` to drop your own Tailscale SSH session while the peer's TUN restarts — let the timer do the recovery instead of reconnecting to hand-fix a broken peer. A reboot while pending also restores last-good before mihomo starts. Inspect `mihomo-guard status` as needed; rejected content is preserved at `/var/lib/mihomo-config/rejected.yaml`.
8. Report the local host and the peer host separately, naming which was which. For each, state hostname and role, Git HEAD/branch/upstream/dirty state, transferred mutable state, rebuild result, relevant service failures, and any intentionally preserved differences or untracked files.
